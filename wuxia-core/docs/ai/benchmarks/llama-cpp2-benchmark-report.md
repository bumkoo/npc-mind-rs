## 1. 벤치마크 목적

Ollama(HTTP API)와 llama-cpp-2(Rust 네이티브 바인딩)의 동일 모델 성능을 비교하여,
칠국춘추 NPC 대화 시스템의 최종 추론 엔진을 결정한다.

### 1.1 테스트 공통 조건

| 항목 | 값 |
|------|-----|
| GPU | NVIDIA RTX 2070 SUPER (8GB) |
| 모델 | gemma-3n-E4B-it-Q4_K_M.gguf (4.3GB) |
| 컨텍스트 | 8192 토큰 (llama-cpp-2) / 2048 토큰 (Ollama) |
| temperature | 0.7 |
| max_tokens | 200 |
| 시나리오 | 소연(素燕) NPC 24턴 대화 |
| GPU 오프로드 | 전 레이어 GPU (36/36) |

### 2.3 프롬프트 평가 비교

llama-cpp-2는 컨텍스트가 커져도 **프롬프트 평가 시간만 선형 증가**하고,
생성 속도는 영향받지 않는다. Ollama는 양쪽 다 저하된다.

```
Prompt 평가 시간 (ms):

        llama-cpp-2                    Ollama (추정)
 Turn │ Ctx_Tok │ Prompt_ms │    Turn │ Ctx_Tok │ Wall_time
──────┼─────────┼───────────┤   ──────┼─────────┼──────────
    1 │     277 │       345 │       1 │    ~630 │    4,600
    6 │     645 │       361 │       6 │   ~1000 │    6,200
   12 │   1,249 │       701 │      12 │   ~1400 │   12,000
   18 │   1,861 │     1,118 │      18 │   ~1700 │   22,000
   24 │   2,485 │     1,464 │      24 │   ~1937 │   38,000

llama-cpp-2: 토큰 9배 → 시간 4배 (효율적, sublinear)
Ollama:      토큰 3배 → 시간 8배 (비효율적, superlinear)
```

## 3. 성능 차이 원인 분석

### 3.1 왜 llama-cpp-2가 빠른가

```
┌─ Ollama 경로 ─────────────────────────────────────┐
│                                                    │
│  게임(Rust) → HTTP 요청 → Ollama 서버 → llama.cpp │
│      ↑           ↑           ↑                     │
│      │       JSON 직렬화   세션 관리/모델 관리      │
│      │       네트워크 지연  KV cache 미보장          │
│      │                                             │
│  게임(Rust) ← HTTP 응답 ← Ollama 서버 ← llama.cpp │
│           JSON 파싱      토큰 스트리밍 변환          │
└────────────────────────────────────────────────────┘

┌─ llama-cpp-2 경로 ────────────────────────────────┐
│                                                    │
│  게임(Rust) → llama-cpp-2 바인딩 → llama.cpp       │
│                  (직접 FFI 호출, 오버헤드 없음)      │
│                                                    │
│  게임(Rust) ← 토큰 직접 반환 ← llama.cpp           │
└────────────────────────────────────────────────────┘
```

| 원인 | 설명 | 영향도 |
|------|------|:------:|
| HTTP 오버헤드 제거 | 매 토큰 JSON 직렬화/역직렬화 없음 | ★★★ |
| KV cache 직접 제어 | 매 턴 새 컨텍스트로 확실한 상태 관리 | ★★★ |
| 프로세스 내 호출 | IPC/네트워크 지연 없음 | ★★☆ |
| 세션 관리 없음 | Ollama의 모델 로드/언로드 스케줄링 없음 | ★☆☆ |

### 3.2 Ollama 압축 적용 후와의 비교

Ollama는 6턴 슬라이딩 윈도우 압축을 적용해야 후반 성능이 개선된다.
llama-cpp-2는 압축 없이도 Ollama 압축 후보다 빠르다.

| 항목 | Ollama 압축 전 | Ollama 압축 후 | llama-cpp-2 (압축 없음) |
|------|:---------:|:---------:|:-------------:|
| Wall T24 | 38.0초 | 11.7초 | **3.5초** |
| 후반/전반 비율 | 8.3x | 2.1x | **1.0x** |
| 구현 복잡도 | - | 요약 로직 필요 | 없음 |

## 4. batch 크기 비교 (llama-cpp-2 내부)

| 항목 | batch=512 | batch=1024 | 차이 |
|------|:---------:|:----------:|:----:|
| 평균 생성 속도 | 46.4 tok/s | 46.8 tok/s | +0.9% |
| 총 Wall time | 60.8초 | 60.6초 | -0.3% |
| Prompt T24 | 1,464ms | 1,468ms | 동일 |
| VRAM compute buffer | 274MB | ~500MB | +226MB |

**결론**: gemma-3n-E4B 24턴(2485tok)에서는 batch=512와 1024 차이 미미.
batch=512가 VRAM 효율적이므로 기본값 유지 권장.
4000tok+ 컨텍스트에서는 batch=1024 고려.

## 5. 개발 엔진 전환 검토: Ollama → llama-cpp-2

### 5.1 평가 매트릭스

| 평가 항목 | Ollama | llama-cpp-2 | 판정 |
|-----------|:------:|:-----------:|:----:|
| 생성 속도 | 16 tok/s | 46.4 tok/s | **llama-cpp-2** |
| 내구성 (24턴) | 후반 급락 | 일정 | **llama-cpp-2** |
| 대화 압축 필요성 | 필수 | 80턴까지 불필요 | **llama-cpp-2** |
| Bevy 통합 | HTTP 비동기 | 프로세스 내 직접 호출 | **llama-cpp-2** |
| KV cache 제어 | 간접 (미보장) | 직접 제어 | **llama-cpp-2** |
| 빌드 난이도 | ✅ 쉬움 (바이너리) | ⚠️ CMake+CUDA 73분 | Ollama |
| 프로토타이핑 | ✅ curl로 즉시 | ⚠️ Rust 코드 필요 | Ollama |
| 디버깅 편의성 | ✅ 독립 프로세스 | ⚠️ 게임과 같은 프로세스 | Ollama |
| API 안정성 | ✅ 안정 | ⚠️ deprecated 경고 있음 | Ollama |
| 멀티 모델 | ✅ 쉬움 | ⚠️ 직접 관리 | Ollama |

### 5.2 llama-cpp-2 전환 시 주의사항

```
1. 빌드 환경 의존성
   - CMake + Ninja + CUDA Toolkit 필수
   - 초기 빌드 73분 (이후 Rust만 변경 시 수초)
   - CI/CD에서 재현 가능한 빌드 스크립트 필요

2. API 불안정성
   - token_to_str() deprecated → token_to_piece() 4인자로 변경
   - Special::Tokenize deprecated
   - llama-cpp-2 크레이트가 llama.cpp 업스트림 추종 중
   - 버전 업데이트 시 breaking change 가능

3. 에러 처리
   - Ollama: HTTP 에러 코드로 깔끔하게 처리
   - llama-cpp-2: GGML_ASSERT 실패 시 프로세스 크래시
     (예: n_batch 초과 시 게임 자체가 죽음)
   → 방어적 코딩 필수 (토큰 수 사전 검증 등)

4. GGML 로그 오염
   - stderr로 CUDA graph 경고 등 대량 출력
   - env GGML_LOG_LEVEL=3이 안 먹히는 경우 있음
   - 로그 리다이렉트 또는 커스텀 로그 콜백 필요

5. 멀티 NPC 동시 대화
   - Ollama: 여러 요청 병렬 가능 (서버가 큐잉)
   - llama-cpp-2: 단일 모델 인스턴스로 순차 처리
   → 동시 NPC 대화 시 큐잉 시스템 직접 구현 필요
```

### 5.3 권장 전략: 하이브리드 전환

```
Phase 2~3 (현재 ~ 도메인 로직):
  └─ Ollama 유지
     - 도메인 로직 개발에 집중
     - LLM 호출은 Ollama HTTP로 간단히 처리
     - 프로토타이핑, 프롬프트 실험에 유리

Phase 4 (Bevy 통합):
  └─ Ollama → llama-cpp-2 전환 시작
     - Bevy 비동기 시스템과 직접 연동
     - KV cache 직접 관리 구현
     - 대화 압축 불필요 → 코드 단순화

Phase 5 (LLM 통합 최적화):
  └─ llama-cpp-2 완전 전환
     - NPC 기억 시스템 (LanceDB) + LLM 통합
     - 멀티 NPC 큐잉 시스템 구현
     - 성능 최종 측정

  ┌─────────────────────────────────────────────────┐
  │ Phase 2~3          Phase 4          Phase 5     │
  │                                                 │
  │  Ollama ──────→ 하이브리드 ──────→ llama-cpp-2  │
  │  (프로토타입)    (전환기)          (프로덕션)     │
  │                                                 │
  │  "빠르게 실험"   "점진적 전환"    "최적 성능"     │
  └─────────────────────────────────────────────────┘
```

### 5.4 전환 판단 근거

llama-cpp-2를 **최종 프로덕션 엔진으로 확정**하되,
**지금 당장 전환하지 않는** 이유:

1. Phase 2~3은 도메인 로직(무공, 심리, 관계) 개발이 핵심
2. LLM 호출 빈도가 낮아 Ollama 속도로도 충분
3. llama-cpp-2 API가 아직 안정화 중 (deprecated 경고)
4. 전환 작업이 Phase 4 Bevy 통합과 자연스럽게 맞물림

## 6. 최종 결론

### 6.1 벤치마크 결론

| 결론 | 내용 |
|------|------|
| **속도** | llama-cpp-2가 Ollama 대비 **2.9배** (평균), Turn 24에서 **9.5배** 빠름 |
| **안정성** | llama-cpp-2는 24턴 동안 성능 저하 **없음** (±2%) |
| **대화 압축** | llama-cpp-2에서는 **80턴까지 불필요** (Ollama는 6턴부터 필수) |
| **batch 크기** | gemma-3n-E4B에서 batch=512와 1024 차이 없음, **512 권장** |

### 6.2 엔진 결정

| 단계 | 엔진 | 사유 |
|------|------|------|
| Phase 2~3 (현재) | **Ollama 유지** | 도메인 로직 개발 집중, 프로토타이핑 유리 |
| Phase 4~5 (Bevy 통합) | **llama-cpp-2 전환** | 성능 3~10배, Bevy 직접 연동, 압축 불필요 |
| 최종 프로덕션 | **llama-cpp-2 확정** | 게임 릴리스 시 필수 |

### 6.3 후속 테스트 과제

| 과제 | 설명 | 우선순위 |
|------|------|:--------:|
| gemma-3-12b 내구성 | llama-cpp-2에서 12b 모델 24턴 테스트 | 높음 |
| gemma-3-4b 비교 | 비핵심 NPC용 경량 모델 성능 확인 | 중간 |
| KV cache 재사용 | 매 턴 새 컨텍스트 대신 cache 유지 방식 테스트 | 중간 |
| 50+ 턴 장기 테스트 | 컨텍스트 한계 도달 시점 정확히 측정 | 낮음 |
| Bevy 비동기 통합 PoC | llama-cpp-2를 Bevy async task로 래핑 | Phase 4 |
