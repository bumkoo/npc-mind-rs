§3-bis. §C 재정의 (Stage 0 심층 — 디자이너 대화 반영)

정정 — 본 절은 §3 불일치② 및 §5 Q3의 초기 서술을 대체한다

초기 서술(§3 ②, Q3): "현 코드는 max-single-axis = §1-C 옵션(a) 이미 구현 → §C 코드 변경 불요, narrative 검증만."

디자이너 심층 검토로 드러난 정정: "코드 변경 불요"는 게이트 로직에 한해서만 옳았다. 실제 §C의 본질은 KICKOFF §1-C의 "sum vs max threshold 산식"이 아니라, 별개의 미결 정책 결정이다:

§C 진짜 질문 (재정의)
게이트는 max@5.0로 두되 — 통과 후 MemoryEntry.content에 threshold(5.0) 초과한 축을 전부 라벨링할 것인가, 현행대로 dominant 1축만 둘 것인가?

현 구현의 결함 (코드 확인): 게이트와 라벨이 단일 dominant_delta max 연산에 뭉뚱그려져 있다. trust Δ=14 ∧ wariness Δ=8 (둘 다 >5.0)인 경우 — 기억은 생성되나 content는 [trust Δ=14.00]만, 유의미한 wariness Δ=8.0이 기억 텍스트에서 소실. 즉 "threshold 초과 축 전부 반영"이 아니라 "초과 축 중 max 1개만".

핵심 — 데이터 가용성: 핸들러는 이미 p에 4축 before/after 8값을 전부 쥐고 있다(event.rs:178 payload). max 1개만 쓰는 건 데이터 부재가 아니라 포맷팅 선택 → 변경 시 게이트·EventStore 불변, content 문자열만 확장.

P-D-C1 — §C content-projection 정책 (FROZEN spec 결정 항목)
옵션내용trade-off
(a) 현행 유지dominant 1축만 라벨기억 텍스트 간결 / 다축 동시 유의 변화 소실 (배신=trust↓+wariness↑인데 trust만 기록)
(b) threshold 초과 전부≥5.0 축 전부, magnitude desc 정렬 라벨충실한 다축 회상 / 게이트·W1·base_delta·D3 회귀 0 (순수 projection) / content 길어짐 — narrative 검증 필요
