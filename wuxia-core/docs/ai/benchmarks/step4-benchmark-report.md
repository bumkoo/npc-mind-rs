### 2.3 품질 개선 — 성공한 규칙 ✅

**세계관 준수:**

```
Step 3 T80: "강력한 마법과 함정으로 둘러싸여 있지"  ← 마법 위반 ❌
Step 4 T80: "강력한 진법과 함정으로 보호받고 있으며" ← 진법 정확 ✅

96턴 전체에서 "마법" 0회 — 세계관 규칙 완벽 작동
```

**요약 구조화:**

```
Step 3 요약: "무협 세계의 뒷골목에서 소연은 문파가 습격당한 소년과..."
             → 자유형 서술, 관계 맥락 누락

Step 4 요약: [관계: 소연→소년 (냉소적 도움), 소년→소연 (의존)]
             [호칭: 꼬맹이]
             [감정: 소연 - 냉담함, 경계심 / 소년 - 불안, 절망]
             사건: ...
             → 관계 태그로 맥락 보존 ✅
```

관계 진화 추적 작동: Day 0(냉소적 도움) → Day 1(계시, 조언) → Day 2(조언자, 보호자)

**정보상 대가 일관성:**

```
Step 3: 후반부에서 대가 없는 정보 무상 제공 ❌
Step 4: T7 "대가는 네가 감당할 수 있는 수준이어야" ✅
        T24 "더 많은 대가가 필요해" ✅
        T52 "적절한 대가를 요구할 거야" ✅
        96턴 전반에 걸쳐 역할 유지
```

**컨텍스트 혼동 해결:**

```
Step 3 T91: "네놈이! 여기서 뭘 하고 있는 거지?" ← 소년을 적으로 오인 ❌
Step 4 T91: "살아 있어. 네놈은 안전한 곳에 있나?" ← 정상 응답 ✅
```

요약 태그의 관계 정보가 슬라이딩 윈도우 후에도 캐릭터 관계를 보존했다.

### 2.4 품질 퇴보 — 실패한 규칙 ❌

**"더 알아봐야 할 게 많아 보이는데" — 재앙적 반복 (71%):**

```

T22: "더 알아봐야 할 게 많아 보이는데."
T23: "더 알아봐야 할 게 많아 보이는데."

이유: 풀문장 반복 → 플레이어 경험 파괴
```

원인: 프롬프트 규칙이 너무 많아서(723 토큰) 모델이 "안전한 문장"에 고착됨. DRY는 n-gram 시퀀스만 감지하므로 매턴 새 컨텍스트에서 재생성되는 이 패턴은 억제 불가.

**"(주변을 둘러보며)" — 지문 고착 (57%):**

```

Step 4: "(주변을 둘러보며)" 약 55/96턴 등장 (57%)
```

"표현 다양성" 규칙이 대사에만 적용되고 지문은 무시됨.

```

  ┌─────────────────────────────────────────────┐
  │           VRAM (전용)                        │

  → Prompt 처리: 7~15초 (가장 큰 병목)
```

### 4.3 공유 GPU 메모리란?

Windows 10/11의 기본 기능으로, VRAM 부족 시 시스템 RAM을 GPU가 빌려 쓰는 메커니즘이다. 8GB VRAM GPU 모두 동일하게 작동한다 (RTX 3060 8GB, RTX 4060 8GB 등).

단, "보너스 메모리"가 아니라 **성능 페널티**: 전용 VRAM ~500GB/s vs 공유 RAM ~50GB/s = 10배 대역폭 차이.

### 4.4 VRAM 12GB+ 환경 예측

```
  VRAM 12GB+ (RTX 3060 12GB, RTX 4070 12GB 등):

  ┌─────────────────────────────────────────────┐
  │           VRAM (전용)                        │
  │  ████████████████  7.6GB / 12.0GB           │  ~500 GB/s (전부 전용!)
  │                    여유 4.4GB ✅             │
  └─────────────────────────────────────────────┘

  공유 RAM 불필요 → 대역폭 병목 해소

  예상 성능:
  ┌──────────────┬──────────────┬──────────┐
  │              │  VRAM 8GB    │  VRAM 12+│
  ├──────────────┼──────────────┼──────────┤
  │  생성 속도   │  ~10 tok/s   │  25~35   │
  │  TTFT        │  7~15초      │  1~2초   │
  │  턴당 체감   │  12~20초     │  3~5초   │
  └──────────────┴──────────────┴──────────┘

  → VRAM 12GB+에서 12b는 2.5~3.5배 빠름
  → TTFT 1~2초면 게임 체감 충분히 쾌적
```

## 5. TTFT 중심 UX 설계

### 5.1 핵심 인사이트: TTFT가 체감 성능을 결정한다

스트리밍 출력에서 사용자가 느끼는 "답답함"은 생성 속도(TPS)가 아니라 **첫 토큰 지연시간(TTFT, Time to First Token)**에 의해 결정된다. 첫 글자가 나온 후에는 읽기 속도만 맞추면 충분하다.

```
  사용자 체감 모델:

  [플레이어 입력] → ⏳ TTFT 대기 → [첫 글자 출현] → 📖 읽기 시작
                     ↑ "답답함" 결정    ↑ "읽기 속도"와 경쟁

  한국어 읽기 속도: 약 3~5 글자/초 (일반 대화)
  gemma-3-12b:     약 10 tok/s ≈ 5~7 글자/초
                   → 읽기보다 빠름! ✅ (생성 속도는 이미 충분)
```

### 5.2 현재 모델별 TTFT

```
  gemma-3-4b:   TTFT ~300ms    ← 즉시 응답 느낌 ✅
  gemma-3-12b:  TTFT ~7~15초   ← "멈춘 건가?" 느낌 ❌ (VRAM 8GB)
  gemma-3-12b:  TTFT ~1~2초    ← 자연스러운 대기 ✅ (VRAM 12GB+)
```

### 5.3 게임 UX 해결: NPC 연출로 TTFT 마스킹

```
  ┌──────────────────────────────┐
  │                              │
  │    소연이 생각에 잠긴다...     │  ← TTFT 대기 중 (7초)
  │    (타이핑 인디케이터 ···)     │     캐릭터 고유 "생각 중" 애니메이션
  │                              │
  ├──────────────────────────────┤
  │  첫 토큰 도착 후:             │
  │                              │
  │  "(눈을 가늘게 뜨며)          │  ← 한 글자씩 스트리밍
  │   흑풍채의 두목은..."         │     읽기 속도에 맞춰 표시
  │                              │
  └──────────────────────────────┘
```

이 접근이면 **12b도 VRAM 8GB에서 실용적**일 수 있다. 7~15초 동안 NPC 고유 애니메이션과 "생각 중" 연출이 자연스러운 대기 경험을 제공한다.

### 5.4 제품 LLM 응답 전략

```
  1. 스트리밍 출력 필수 (한번에 전체 출력 X)
  2. TTFT 중 NPC 연출 (생각 중... 애니메이션)
  3. 생성 속도는 읽기 속도(3~5자/초) 이상이면 OK
  4. TTFT가 진짜 최적화 타겟
     → KV Cache 재사용으로 TTFT 단축 가능 (향후 과제)
```

```
  │                                                                 │
```

### 6.3 DRY/Penalties 설정 근거

| 환경 | DRY+Penalties | 근거 |
|------|:-------------:|------|
| 4b (VRAM 8GB) | **ON (필수)** | 반복 패턴 70%+ 발생, 억제 필수 |
| 12b (VRAM 8GB) | **선택적 (기본 OFF)** | 반복 0%, 속도 개선 미미 (+0.7tok/s), 불필요한 오버헤드 제거 |
| 12b (VRAM 12+) | **기본 OFF** | 반복 0%, Prompt 병목 해소 시 DRY 7% 오버헤드가 체감됨 |

DRY/Penalties 오버헤드 분석 (Step 3 측정치):

```
  생성 단계 오버헤드: ~7% (Step 3 기준)

  4b (64 tok/s):   DRY 제거 시 → ~68.5 tok/s (+4.5 tok/s, 유의미)
  12b (10 tok/s):  DRY 제거 시 → ~10.7 tok/s (+0.7 tok/s, 미미)
                   ↑ 진짜 병목은 공유RAM 대역폭 (TTFT 7~15초)

  12b + VRAM 12GB+ (30 tok/s 예상):
                   DRY 제거 시 → ~32 tok/s (+2 tok/s, 체감됨)
                   ↑ Prompt 병목 해소 후 DRY 오버헤드가 주요 변수
```

## 7. 기술적 발견 사항

### 7.1 프롬프트 크기와 반복의 상관관계

```
  프롬프트 크기 vs 반복 고착:

  시작 ctx
  800 ┤          ★ Step 4 (723 ctx, 71% 반복)
      │
  600 ┤
      │
  400 ┤
      │    ★ Step 3 (295 ctx, 62% 반복)
  200 ┤
      └────┬──────┬──────┬──────┬──────→ 반복률 (%)
          20     40     60     80

  4B 모델에서 프롬프트 크기↑ → 자유도↓ → "안전한 문장" 고착↑
  → 프롬프트는 350~400 토큰 이내가 4B 모델의 최적 범위
```

### 7.2 모델 크기와 반복 억제 능력

```
  파라미터 수 vs 자체 반복 억제:

  반복률
  80% ┤  ★ 3n-E4B (71%)
      │  ★ 3-4b (70%)
  60% ┤
      │
  40% ┤
      │
  20% ┤
      │
   0% ┤                    ★ 3-12b (0%)
      └────┬──────┬──────┬──────→ 파라미터 (B)
           4      8      12

  12B에서 반복 억제 능력이 비선형적으로 급증
  → 4B 모델은 DRY/Penalties 외부 장치 필수
  → 12B 모델은 자체 억제로 충분, 외부 장치 불필요
```

### 7.3 gemma-3n-E4B vs gemma-3-4b 아키텍처 차이의 영향

두 모델 모두 ~4B급이지만 성능이 다른 이유:

| 특성 | gemma-3n-E4B | gemma-3-4b |
|------|:------------:|:----------:|
| 아키텍처 | MatFormer (동적 추론) | Dense Transformer |
| 생성 속도 | 44 tok/s | 64 tok/s (+45%) |
| 품질 | 6.2/10 | 7.3/10 (+18%) |
| 반복 패턴 | "풀문장 고착" | "접속사 고착" |
| 외국어 누출 | 0 | 14개 |

gemma-3-4b(Dense)가 속도·품질 모두 우세. MatFormer의 동적 추론 특성이 한국어 무협 대화에서는 약점이 됨.
