## 2. 테스트 인프라

### 2.1 LLM 서빙

| 항목 | 내용 |
|------|------|
| 추론 엔진 | Ollama (HTTP API) |
| API 엔드포인트 | `http://localhost:11434/api/chat` |
| 설정 | `num_ctx=2048`, `temperature=0.7`, `num_predict=200` |

### 2.2 KV Cache 현실 — 핵심 발견사항

벤치마크 과정에서 발견한 **가장 중요한 기술적 사실**:

```
VRAM 예산 (RTX 2070S 8GB):

  모델 가중치 + CUDA 오버헤드 + KV Cache = 8GB 이내여야 함

  gemma3:12b (7.6GB 모델)의 경우:
    모델 가중치:  7.6 GB
    CUDA 오버헤드: 0.3 GB
    KV Cache 여유: 0.1 GB  ← 거의 없음!
    
  → 128K 컨텍스트 윈도우는 순수 이론값
  → 실제 사용 가능: ~2048 토큰
  → 부족 시 Ollama가 CPU 오프로드 → 극심한 속도 저하
```

**결론**: 모든 모델을 `num_ctx=2048`으로 통일하여 공정 비교해야 하며, 모델 스펙상 컨텍스트 윈도우 크기는 RTX 2070S에서 무의미하다.

### 2.3 2048 토큰 예산 배분 (게임 설계)

```
시스템 프롬프트 (소연 성격):  ~500 토큰
NPC 기억 (LanceDB 검색):     ~300 토큰
관계 상태 정보:              ~100 토큰
최근 대화 기록:              ~600 토큰
플레이어 현재 입력:          ~100 토큰
모델 응답 버퍼:              ~400 토큰
────────────────────────────────────
합계:                       ~2000 토큰
```

## 5. 대화 압축 테스트 (gemma3n:e4b + Sliding Window)

### 5.1 압축 방식

"슬라이딩 윈도우" 기법으로 오래된 대화를 요약하여 프롬프트 크기를 일정하게 유지한다.

```
Window = 6 (최근 6턴은 전문 보존)

  T1~T6:  전부 전문으로 전송 (압축 불필요)
  T7:     [T1 요약] + T2~T7 전문
  T12:    [T1~T6 요약] + T7~T12 전문
  T24:    [T1~T18 요약] + T19~T24 전문

  메시지 수: 최대 14개 (고정)
  프롬프트 토큰: ~1300 내외로 안정
```

### 5.2 압축 전후 비교

| 항목 | 압축 전 | 압축 후 (window=6) | 개선 |

## 6. 최종 선정

### 6.1 결론

**선정 모델: `gemma3n:e4b` + 대화 압축 (window=6)**

| 항목 | 값 |
|------|-----|
| 모델 | gemma3n:e4b (Google Gemma 3n) |
| 아키텍처 | MatFormer — 4B active + 4B PLE |
| 양자화 | Q4_K_M (기본) |
| VRAM 사용 | ~3900MB (여유: ~4100MB) |
| 실효 컨텍스트 | 2048 토큰 |
| 평균 속도 | ~16 tok/s |
| Wall time | 4~12초 (압축 적용 시) |
| 대화 방식 | 슬라이딩 윈도우 압축 (최근 6턴 전문 + 이전 요약) |

### 6.2 선정 사유

1. **품질 우위**: 3개 후보 중 유일하게 비밀 보호, 감정 트리거, 캐릭터 내면 표현을 모두 통과
2. **압축으로 성능 해결**: Wall time 38초 → 12초 이내로 개선, 게임 연출로 커버 가능한 수준
3. **VRAM 안정**: 4100MB 여유 — 게임 렌더링, 벡터DB 등 다른 시스템에 할당 가능
4. **확장 가능**: window 크기 조정으로 품질-속도 트레이드오프 튜닝 가능

### 6.3 탈락 모델 사유 요약

| 모델 | 탈락 사유 |
|------|----------|
| gemma3:12b | VRAM 8GB에서 구동 불가 (CPU 오프로드, T1 타임아웃) |
| gemma3n:e2b | 품질 붕괴 (T9부터 "꽤나" 무한 반복 루프) |
| gemma3:4b | 캐릭터 깊이 부족 (비밀 쉽게 노출, 감정 피상적, 후반 반복) |
| qwen3:8b | 한국어 품질 미달 |
| llama3.2:3b | 한국어 지원 불가 |
| phi4-mini:3.8b | 캐릭터 일관성 부족 |
| mistral:7b | 한국어 지원 불가 |

### 6.4 gemma3:4b — 대안으로 보류

gemma3:4b는 속도(82 tok/s)와 안정성이 뛰어나므로 다음 상황에서 대안으로 고려:

- 동시에 여러 NPC 대화가 필요한 경우 (멀티 NPC)
- 비핵심 NPC (상점 주인, 행인 등)의 간단한 대화
- 실시간 전투 중 빠른 반응이 필요한 경우

## 7. 게임 적용 아키텍처

### 7.1 현재 (MVP Sprint 1) — Ollama 기반

```
┌─────────────┐     HTTP/JSON     ┌──────────────┐
│  게임 로직   │ ←──────────────→ │   Ollama     │
│  (Rust)     │   /api/chat       │  gemma3n:e4b │
└─────────────┘                   └──────────────┘

대화 흐름:
  1. 시스템 프롬프트 (소연 성격)
  2. [오래된 턴 요약] (슬라이딩 윈도우 압축)
  3. [최근 6턴 전문]
  4. 플레이어 입력
  → Ollama 호출 → 소연 응답 (4~12초)
```

### 7.2 최종 (Phase 5) — llama-cpp-2 직접 통합

```
┌──────────────────────────────────────┐
│              Bevy ECS                │
│  ┌──────────┐    ┌────────────────┐  │
│  │ 대화 시스템│    │ llama-cpp-2   │  │
│  │ (Rust)   │←──→│ KV cache 직접 │  │
│  └──────────┘    │ 제어          │  │
│                  └────────────────┘  │
│  ┌──────────┐    ┌────────────────┐  │
│  │ 기억 시스템│←──→│   LanceDB     │  │
│  └──────────┘    └────────────────┘  │
└──────────────────────────────────────┘

장점:
  - KV cache 직접 제어 → 대화 압축 불필요할 수 있음
  - HTTP 오버헤드 제거
  - Bevy 비동기 시스템과 직접 연동
```

### 7.3 NPC 기억 구조 (최종 설계)

```
NPC의 "뇌" 구조:

  ┌─ 정체성 (불변) ──────────────────────────┐
  │  시스템 프롬프트: 소연의 성격, 배경, 말투    │  ~500토큰
  └──────────────────────────────────────────┘
  
  ┌─ 장기 기억 (LanceDB) ──────────────────────┐
  │  벡터 검색으로 관련 기억만 추출               │  ~300토큰
  │  "이 소년은 3일 전 처음 만남"                 │
  │  "혈교 언급 시 감정 동요 있었음"               │
  └──────────────────────────────────────────────┘
  
  ┌─ 중기 기억 (대화 요약) ────────────────────┐
  │  오래된 대화를 압축한 요약                    │  ~200토큰
  │  "어제 정보 거래에 합의함"                    │
  └──────────────────────────────────────────────┘
  
  ┌─ 단기 기억 (최근 대화) ────────────────────┐
  │  최근 6턴 전문 보존 (생생한 맥락)             │  ~600토큰
  └──────────────────────────────────────────────┘
  
  ┌─ 현재 (플레이어 입력) ─────────────────────┐
  │  지금 플레이어가 한 말                        │  ~100토큰
  └──────────────────────────────────────────────┘
  
  ┌─ 응답 버퍼 ────────────────────────────────┐
  │  모델이 생성하는 소연의 대답                   │  ~300토큰
  └──────────────────────────────────────────────┘
  
  합계: ~2000토큰 (2048 이내)
```

## 9. 참고: Ollama vs llama-cpp-2

현재 Ollama로 측정한 결과는 "최악의 시나리오"에 해당한다.

| 항목 | Ollama API | llama-cpp-2 (Rust) |
|------|:----------:|:------------------:|
| KV cache 제어 | 간접적 (keep_alive) | 직접 제어 |
| cache 재사용 보장 | ❌ 미보장 | ✅ 보장 |
| HTTP 오버헤드 | 있음 | 없음 |
| 설치 편의성 | ✅ 쉬움 | ⚠️ 빌드 필요 |
| 용도 | 프로토타이핑, 실험 | 프로덕션 게임 |

**핵심**: Ollama에서 동작하면 llama-cpp-2에서는 같거나 더 빠르다. 따라서 모델 선택은 유효하며, 최종 성능은 Phase 5에서 재측정한다.
