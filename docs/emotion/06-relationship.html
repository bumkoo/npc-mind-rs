관계 반영

"관계"는 감정에 두 번 관여한다 — ① 감정 발생 시 modifier로 증폭/억제하고, ② 발생한 감정이 다시 관계 4축을 갱신한다. 둘은 완전히 다른 메커니즘이라 분리해 본다.

두 개념을 혼동하지 말 것 (A) modifier 산출 = Relationship::modifiers() — affinity·trust → 4 배율 (1단계로 투입)
(B) 4축 갱신 = update_axes_from_emotion — 감정 → 관계 변동 (6단계 산출)

1(A) modifier 산출

domain/relationship/mod.rs · Relationship::modifiers()

1단계 공식의 modifier는 여기서 나온다. affinity와 trust 두 축만 쓴다(respect·wariness 미사용). ±100 raw 값에 1/100 스케일 튜닝 가중치를 직접 곱한다.

필드산식w 값 (default)곱해지는 분기
intensity_multipliermax(0, 1 + affinity × w)0.005타인 행동(Admir./Reproach)
trust_modifier1 + trust × w0.003〃 (intensity와 곱)
empathy_modifiermax(0, 1 + affinity × w)0.003HappyFor / Pity
hostility_modifiermax(0, 1 − affinity × w)0.003Resentment / Gloating
부호의 묘 hostility만 1 − affinity×w다. 그래서 적대 관계(affinity 음수)면 −(−affinity)가 양수가 되어 hostility_modifier > 1 → 시기·고소함이 증폭된다. 반대로 친밀(affinity 양수)이면 hostility < 1로 억제. 중립(0)이면 4필드 전부 1.0.
affinity=+80(친밀), trust=+50 · affinity=−80(원수)
친밀: intensity = 1+80×0.005 = 1.40 · empathy = 1+80×0.003 = 1.24 · hostility = 1−80×0.003 = 0.76 원수: intensity = 1−80×0.005 = 0.60 · empathy = 0.76 · hostility = 1+80×0.003 = 1.24 trust_mod = 1 + 50×0.003 = 1.15
Phase 2.4 검토 예정 현 modifiers()는 affinity·trust 2축만 사용 — respect·wariness는 (B) 4축 갱신엔 쓰이나 modifier 산출엔 미반영(설계 근거 문서 부재, 코드 구조에서 역추론). 비판적 검토로 도출한 7개 항목(문서화 ①②③④ + 신규 부채 ⑤⑥⑦)과 이를 한 번에 푸는 통합 재설계, 그리고 PerceivedSituation 별도 트랙은 아래 §5에 정리한다.

"부정 감정" 분류의 비대칭 A− Forgiveness 룰의 "부정 감정"은 OCC valence가 아니라 base_delta의 affinity 부호 기준이다. 그래서 Pity는 OCC상 부정 반응이지만 affinity +10이라 제외된다 — "인색한 사람의 동정심 증폭"이라는 서사 모순을 피하기 위함(회고 §W2).
약점 — Beat 개수가 관계 변경량을 좌우 (단계 미지정) (B) 4축 갱신을 호출하는 지점은 현재 셋이다: stimulus_policy::process_beat_transition(Beat 전환마다) · relationship_policy::handle_dialogue_end(대화/Scene 종료, is_chitchat 게이트) · handle_relationship_update_with_cause(외부 사건). 문제는 첫째다.
  • 비트 多 → 변경 大 — Beat 전환마다 update_axes_from_emotion이 같은 부호 Δ를 누적한다. 5비트 씬(전환 ~4회)은 2비트 씬보다 관계가 훨씬 크게 흔들린다. 즉 작가가 한 사건을 몇 조각으로 쪼갰는가(설계 아티팩트)가 서사적 의미와 무관하게 변경량을 결정한다.
  • 이중 적용 소지 — 한 씬에서 Beat 전환 갱신 + 종료 시 갱신이 둘 다 같은 helper(apply_emotions_to_relationship)를 거친다 → 같은 씬의 감정이 두 번 반영될 수 있다. (호출 지점 grep 확인 / 한 씬에서 둘이 동시에 도는 통합 테스트는 미확인 → "구조상 가능".)
  • clamp만이 제동 — ±100(wariness 0~100)이 상한은 막지만, 상한 전까진 비트 수에 비례해 누적. 점진 감쇠·시간 회복 없음.
차후 방향 — 호출 횟수 비의존을 얻는 두 경로 (단계 보류): 목표 아키텍처(relationships.md §3.2)는 Inner Loop axes 불변 · Outer Loop(Scene 경계) 갱신을 지향한다. 호출 횟수 불변성은 다음 둘 중 하나로 얻을 수 있고, 둘은 순효과가 수학적으로 동일하다:
  • (i) Scene 경계 1회 적용 — Beat 전환 갱신을 제거하고 씬 종료 시 1번만 적용. 비트를 몇 개로 쪼개든 무관. 추가 상태 없음·단순. (로드맵 기존 방향.)
  • (ii) 차분(difference) 기반 per-beat 공식 — Δ를 감정 레벨이 아니라 직전 대비 감정 변화에 비례시킨다. 합이 망원합(telescoping)으로 상쇄돼 호출 횟수와 무관:
    현재(레벨): Σ w·eᵢ = w(e₁+…+eₙ) → n에 비례 (발산) 차분: Σ w(eᵢ−eᵢ₋₁) = w(e_end−e₀) → n 무관
    실시간 증분(턴마다 관계가 움직이는 연출)이 가능하나, 관계마다 "직전 감정 벡터" 저장(상태·replay 영향)이 필요하다.
동치와 진짜 설계점: (ii)의 순효과 = w(e_end − e_start) = (i)을 끝값으로 계산한 것과 같다. 또한 base_delta가 에피소드 단위 충격("분노 1회 = 신뢰 −25")으로 작성돼 있어, 자연스러운 적용 단위는 비트/순간이 아니라 에피소드(씬)다 → 단순성에선 (i)이 유리, (ii)는 실시간 증분이 필요할 때만 값어치. 단 (i)·(ii) 모두 끝값만 쓰면 순간 피크를 놓친다(분노 0.9 치솔았다 종료 시 0 → 순변화 0 → 관계 변화 0). 따라서 핵심 결정은 "씬의 대표 감정"을 끝값·누적·피크 중 무엇으로 잡느냐이고, 그 산정이 곧 Scene Boundary Reflection의 역할이다. (구현 단계 배정은 보류.)

3무협 워크드 예시 — 임충 산신묘

임충이 육겸의 음모를 듣고 Anger 0.95 (단위 테스트 실제값)

입력 관계: trust 50 · affinity 40 · respect 30 · wariness 5
임충 HEXACO: Sincerity 0.7 / Forgiveness −0.7 / Prudence 0.8 → modifier 3단 적용: ×1.2(trust) → ×1.5(전역, Anger 부정) → ×0.8(전역)

modifier = { trust 1.44, affinity 1.2, respect 1.2, wariness 1.2 } trust : −25 × 0.95 × 1.44 = −34.2 → 50−34.2 = 15.8 affinity : −10 × 0.95 × 1.2 = −11.4 → 40−11.4 = 28.6 respect : 0 × … = 0 → 30.0 wariness : +25 × 0.95 × 1.2 = +28.5 → 5+28.5 = 33.5

한 번의 분노가 신뢰를 절반으로 깎고 경계심을 6배로 끌어올린다. 이 값이 다시 modifiers()로 들어가 다음 대화의 감정 강도를 바꾼다 — 루프가 닫힌다.

BondStatus 게이트 상대가 사망(Deceased)·관계 해소(Resolved)·휴면(Dormant)이면 accepts_live_input()가 false → 감정이 아무리 커도 4축은 변동하지 않는다. Active·Reactivating만 통과. 또한 Pride/Shame는 자기 감정이라 호출 측에서 별도 가드(B-D12).

4실제 코드

▸ mod.rs — Relationship::modifiers() domain/relationship/mod.rs 
pub fn modifiers(&self) -> RelationshipModifiers {
    let affinity = self.affinity.value();  // ±100 raw
    let trust = self.trust.value();
    let p = profile();
    RelationshipModifiers {
        intensity_multiplier: (1.0 + affinity * p.rel_affinity_intensity_weight).max(0.0),
        trust_modifier:        1.0 + trust * p.rel_trust_emotion_weight,
        empathy_modifier:     (1.0 + affinity * p.rel_affinity_empathy_weight).max(0.0),
        hostility_modifier:   (1.0 - affinity * p.rel_affinity_hostility_weight).max(0.0),
    }
}
▸ mapping.rs — update_axes_from_emotion() + hexaco_modifier domain/relationship/mapping.rs 
pub fn update_axes_from_emotion(rel: &mut Relationship,
    emotion: EmotionType, intensity: f32, hexaco: &HexacoProfile) {
    if !rel.bond_status().accepts_live_input() { return; }   // 게이트

    let base = base_delta(emotion);
    let m = hexaco_modifier(emotion, hexaco);
    let delta = AxisDelta {
        trust:    base.trust    * intensity * m.trust,
        affinity: base.affinity * intensity * m.affinity,
        respect:  base.respect  * intensity * m.respect,
        wariness: base.wariness * intensity * m.wariness,
    };
    rel.apply_delta(&delta);   // 4축 자동 clamp
}

// hexaco_modifier 핵심 룰 (임계 0.5)
if hexaco.honesty_humility.sincerity.value() > 0.5 {
    m = m.scale_axis(AxisKind::Trust, 1.2); }
if hexaco.agreeableness.forgiveness.value() < -0.5
   && is_negative_emotion(emotion) {
    m = m.combine_uniform(1.5); }
if hexaco.conscientiousness.prudence.value() > 0.5 {
    m = m.combine_uniform(0.8); }

5Phase 2.4.3 개선 계획 · modifiers() 정밀화

domain/relationship/mod.rs · RelationshipModifiers · tuning.rs

(A) modifier 산출의 비판적 검토로 7개 항목을 도출했다 — 문서화된 ①②③④에 신규 부채 ⑤⑥⑦을 더한다. 개별 패치 대신 하나의 통합 재설계로 묶으면 ①–⑦이 동시에 풀린다. 코드 작성 전 설계 합의(check-in ①) 단계의 명세이며, FROZEN spec(.md)은 방향 확정 후 별도 작성한다.

통합 원리 — 4축을 두 기능으로 분리 trust = 스테이크/기대 축 → 대칭(Admiration·Reproach 양쪽 증폭, 배신감). 4축 중 유일하게 대칭.
affinity · respect = 따뜻함/존경 렌즈 → Admiration↑ / Reproach↓ (관대·봐줌).
wariness = 위협 렌즈 → Admiration↓ / Reproach↑ (의심).

목표 구조 (타인 행동 가지 — Admiration/Reproach)

목표 final = base_val × weight × magnitude(trust) × valence_tilt(affinity·respect·wariness)
그룹 내 가산 · 그룹 간 1회 곱 · 그룹마다 단일 clamp
magnitude = clamp(1 + trust·w_t, FLOOR, CEIL) tilt(Admiration) = clamp(1 + affinity·w_a + respect·w_r − wariness·w_w, FLOOR, CEIL) tilt(Reproach) = clamp(1 − affinity·w_a − respect·w_r + wariness·w_w, FLOOR, CEIL) final = base_val × weight × magnitude × tilt

제안 FLOOR=0.5 · CEIL=1.5 — personality weight 범위와 대칭. 이 단일 clamp가 ①(하한·부호반전)과 ②(상한·폭주)를 한 번에 충족한다. 기존 intensity_multiplier × trust_modifier의 두 독립 증폭 곱(affinity·trust)을 제거하고 trust=magnitude / affinity=tilt로 역할을 가른다.

⑦ 워크드 — 두 경우가 모두 나온다 Reproach 배율 = (1−affinity·w)(1+trust·w)… 의 균형이 결정 (w=0.003 예시):
따뜻한데 안 믿는 친구(aff+80/trust−20): 0.76×0.94 = 0.71 → 봐줌 · 안 친한데 믿던 동료(aff+10/trust+80): 0.97×1.24 = 1.20 → 부각(배신) · 둘 다 높은 절친(+80/+80): 0.76×1.24 = 0.94 → 팽팽.

④ 안정성 — 렌즈의 비대칭 피드백

왜 ④만 안정화 장치가 필요한가 동일한 tilt 구조라도 base_delta 부호 때문에 한쪽만 발산한다:
respect 경로 = 음의 피드백(자기 수렴) — 높은 respect → Reproach 억제 → respect 하락폭(base_delta −25)도 작아짐 → respect 유지. 안정.
wariness 경로 = 양의 피드백(발산 위험) — 높은 wariness → Reproach 증폭 → wariness 상승(base_delta +10)도 커짐 → 더 증폭. 감쇠(decay) 또는 히스테리시스 필수.

제약 · 전제 (계획 수립 시 필독)

  • PAD 벤치마크 영향 — 감정 강도가 바뀌면 하류 PAD가 바뀐다. docs/emotion/pad-anchor-score-matrix.md의 잠긴 20개 기대값 재검증 필수. 신규 w/clamp는 기대값을 보존하도록 튜닝하거나, 편차 발생 시 Bekay 명시 승인 없이 기대값 변경 금지.
  • 범위 = 타인 행동 가지(Admiration/Reproach) — intensity_multiplier·trust_modifier 경로만 1차 대상. empathy_modifier·hostility_modifier(HappyFor/Pity/Resentment/Gloating)는 감정 종류가 valence를 내포하므로 별도 결정. 단 RelationshipModifiers struct를 공유하므로, struct 재설계 시 두 필드의 호환(현행 유지 vs 렌즈 모델 통합)을 함께 명세할 것.
  • Pride/Shame 무영향 — 자기 행동은 appraisal/action.rs에서 modifier=1.0 하드코딩이라 이 필드들을 쓰지 않는다.
  • gentleness와의 이중 적용 주의 — "봐줌"은 이미 praiseworthiness_weight에서 gentleness(성격·대상 무관)로 구현돼 있다(Admir. +Gen / Reproach −Gen). 관계 렌즈(affinity·대상별)는 그 위에 곱해진다 — 중복이 아니라 대상-특이성 추가. 온화한 NPC × 친한 상대면 Reproach가 과도히 눌릴 수 있으니 w 튜닝 시 합산 효과를 확인.
  • 신규 튜닝 파라미터 — tuning.rs에 rel_affinity_tilt_weight / rel_respect_tilt_weight / rel_wariness_tilt_weight + REL_MOD_FLOOR / REL_MOD_CEIL 추가. 기존 rel_trust_emotion_weight는 magnitude로 재사용.
별도 트랙 — PerceivedSituation 층 (Phase 2.4 밖 · 신규 검토 필요) 위 재설계는 이미 정해진 praiseworthiness에 뒤이은 강도 조절이다. 다음 둘은 감정 발생 이전의 지각 단계 문제라 modifier로는 풀 수 없고, PerceivedSituation 필터 레이어의 신규 작업으로 별도 검토한다:
  • 행동 심각도 임계("큰 배신") — 현재 |praiseworthiness|는 선형으로만 들어가고(praiseworthiness_weight는 부호만 사용·크기 미사용), "사소한 잘못은 봐주고 큰 배신은 절친일수록 폭발"하는 비선형/임계가 코드에 없다.
  • praiseworthiness 부호 재해석 — affinity·wariness가 지각된 praiseworthiness 자체를 보정(중립 행동을 호의적/위협적으로 재해석, 경계 시 부호 반전 가능). 강도 조절을 넘어 "어떤 감정이 발화되는가"를 바꾸는 수준.
